# myIO Bridge

A bridge that connects [myIO](https://www.myio.hu) smart home controllers to [Home Assistant](https://www.home-assistant.io) via MQTT. It polls myIO servers over HTTP, publishes state changes to MQTT, and forwards Home Assistant commands back to the myIO devices.

## How it works

The project consists of two executables:

- **discovery** — queries one or more myIO servers, auto-detects outputs (switches, lights, covers, sensors), and generates a `bridge.json` configuration file.
- **bridge** — reads `bridge.json`, connects to an MQTT broker, publishes Home Assistant auto-discovery messages, and runs the poll/command loop.

```
myIO server ──HTTP──▶ bridge ──MQTT──▶ Home Assistant
                         ▲
                    bridge.json
                    (generated by discovery)
```

When Home Assistant restarts, it sends a birth message (`homeassistant/status = online`). The bridge detects this and automatically republishes all discovery messages so entities reappear without restarting the bridge.

When the MQTT broker restarts (and retained state messages are lost), the bridge detects the reconnection and schedules a full state resync: on the next poll cycle it republishes the current state of all entities, restoring the broker's retained messages and keeping Home Assistant in sync.

Both can also be triggered by hand from Home Assistant: the `myIO bridge` device has two `config` buttons, **Discovery újraküldése** (`<prefix>/bridge/rediscover`) and **Állapot újraszinkronizálása** (`<prefix>/bridge/resync`, takes effect at the next poll). Payload `PRESS`; neither sends an extra request to the myIO devices. There is deliberately no restart button — the Web UI provides that.

## Prerequisites

- CMake ≥ 3.25
- Clang or MSVC with C++23 support
- [vcpkg](https://github.com/microsoft/vcpkg) with the following packages:

```
vcpkg install boost-asio boost-beast boost-json boost-system boost-thread boost-mqtt5
```

## Building

```bash
cmake -B build -S . -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake
cmake --build build
```

Or with Ninja:

```bash
cmake -B build -S . -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake -G Ninja
ninja -C build
```

Outputs: `build/discovery` and `build/bridge`.

## Usage

### Step 1 — Create the discovery input file

Copy `data/discovery_input.example.json` to `data/discovery_input.json` and fill in your myIO server details:

```json
{
  "servers": [
    {
      "id": "lighting",
      "host": "192.168.1.10",
      "port": 80,
      "user": "admin",
      "password": "admin"
    }
  ]
}
```

### Step 2 — Run discovery

```bash
./discovery discovery_input.json bridge.json
```

This queries each server's `/d_sens_out.json` endpoint and writes a fully populated `bridge.json`. All outputs are initially set to `"enabled": false`.

Re-running discovery on an existing `bridge.json` merges per entry (matched by `id`, within server and section `pca`/`relays`/`pwm`/`sensors`/`covers`) and prints a report of what changed:

- The existing entry is the base: `enabled`, `type`, `writable`, `device_class`, `log_threshold` and any other user key are preserved; keys missing from it are filled in from the device.
- `name` and `_`-prefixed diagnostic fields are refreshed from the device (a user-edited name is overwritten, since the tool cannot tell it from a device name). Cover `up`/`down` objects are merged the same way.
- Server-level keys: existing wins, gaps are filled.
- New outputs reported by the device are added (`enabled: false`) and listed in the report.
- Entries the device no longer reports are **kept** and listed ("review/remove manually") — nothing is deleted.
- A server whose query fails keeps its existing config unchanged (reported); a server absent from the input file is kept unchanged.

### Step 3 — Edit bridge.json

Open `bridge.json` and configure:

- Set the MQTT broker connection under `"mqtt"`.
- For each output, set `"enabled": true` and choose the appropriate `"type"` (see [Entity types](#entity-types) below).

Optional per-server tuning fields (defaults shown; omit to use the default):

| Field | Default | Meaning |
|---|---|---|
| `poll_interval_sec` | `5` | How often the server is polled over HTTP (must be > 0). |
| `sensor_log_threshold` | `0.1` | Minimum sensor change (°C / unit) that gets logged; `0` logs every publish. |
| `log_startup_sync` | `false` | Log entity states during startup/resync. |
| `log_debug` | `false` | Log the `[coalesce]` / `[latency]` measurement lines (sizing `coalesce_window_ms`); must be a boolean. |
| `coalesce_window_ms` | `5` | How long to wait after the first command so sibling commands from the same HA action batch into one POST; `0` disables batching. See [Command latency & TCP delayed-ACK](#command-latency--tcp-delayed-ack). |

```json
{
  "mqtt": {
    "host": "192.168.1.100",
    "port": 1883,
    "client_id": "myio_bridge",
    "user": "",
    "password": "",
    "topic_prefix": "myio"
  },
  "servers": [
    {
      "id": "lighting",
      "host": "192.168.1.10",
      "port": 80,
      "user": "admin",
      "password": "admin",
      "poll_interval_sec": 2,
      "coalesce_window_ms": 5,
      "pca": [
        { "id": 2001, "name": "Living room light",   "type": "switch", "enabled": true  },
        { "id": 2002, "name": "Hallway dimmer",       "type": "light",  "enabled": true  },
        { "id": 2005, "name": "Irrigation valve",     "type": "number", "enabled": true  },
        { "id": 2010, "name": "Unused output",        "type": "switch", "enabled": false }
      ],
      "relays": [
        { "id": 3001, "name": "Garden pump",          "type": "switch", "enabled": true  }
      ],
      "pwm": [
        { "id": 101,  "name": "Bedroom dimmer",       "type": "light",  "enabled": true  },
        { "id": 102,  "name": "Mixing valve",         "type": "number", "enabled": true  }
      ],
      "sensors": [
        { "id": 1,    "name": "Outdoor temperature",  "enabled": true  }
      ],
      "covers": [
        {
          "id": "living_room_blind",
          "name": "Living room blind",
          "enabled": true,
          "up":   { "type": "pca", "id": 2003 },
          "down": { "type": "pca", "id": 2004 }
        }
      ]
    }
  ]
}
```

Disabled entries (`"enabled": false`) are removed from Home Assistant's entity registry automatically via MQTT undiscovery messages.

Optional per-output keys (`pca`, `relays`, `pwm`):

| Key | Default | Meaning |
|---|---|---|
| `writable` | `true` | `false` → read-only entity without `command_topic`; commands to its `/set` topic are dropped. See [Entity types](#entity-types). |
| `device_class` | — | HA device class, only used when the entity is a `binary_sensor` (read-only switch/relay), e.g. `"door"`. Must be a non-empty string if present. |

#### Config validation

The bridge refuses to start (config error) if:

- the `mqtt` section is missing, or `servers` is missing or empty;
- `poll_interval_sec` ≤ 0, or `coalesce_window_ms` is outside 0..10000;
- `mqtt.topic_prefix`, a server `id` or a cover `id` is empty or contains `/`, `+` or `#` (each must be a single topic level);
- a server `id` is `bridge` (reserved for the bridge availability topic);
- `mqtt.port` or a server `port` is outside 1..65535;
- a cover lacks the `up` or `down` object, or an endpoint `type` is not `"pca"` or `"relay"`;
- `writable` is not a boolean, or is `false` on a cover or on a `cover_up`/`cover_down` output.

`./bridge --check-config bridge.json` runs the same checks without connecting anywhere (exit 0 = valid, 1 = the error on stderr). The Web UI runs it on every `bridge.json` save and refuses an invalid file.

### Step 4 — Run the bridge

```bash
./bridge bridge.json
```

The bridge will:
1. Connect to the MQTT broker.
2. Publish Home Assistant auto-discovery messages for all enabled entities.
3. Start polling each server at the configured interval (default: 5 s).
4. Listen for commands from Home Assistant and forward them to the myIO servers.

Press `Ctrl+C` to stop gracefully.

## Entity types

The `"type"` field and the `"writable"` flag of each output determine its HA entity and the commands it accepts:

| Output | `"type"` | `writable: true` (default) | `writable: false` |
|---|---|---|---|
| PCA | `switch` (default for unknown values) | `switch` | `binary_sensor` (ON/OFF) |
| PCA | `sensor_output` | `switch` | `binary_sensor` |
| PCA | `light` | `light` (brightness if the output is PWM-capable) | `sensor` (%) |
| PCA | `number` | `number` (0–100 %) | `sensor` (%) |
| Relay | any non-cover type | `switch` | `binary_sensor` |
| PWM | `light` (and any non-`number` type) | `light` with brightness | `sensor` (%) |
| PWM | `number` | `number` (0–100 %) | `sensor` (%) |
| PCA / relay | `cover_up` / `cover_down` | no entity | config error |
| Cover | `covers` section (`up` + `down`) | `cover` | config error |
| Sensor | *(sensors section)* | `sensor` (read-only) | — |

**Cover endpoints have no entity of their own** while their cover is `enabled`: any PCA/relay output referenced by an enabled cover's `up`/`down`, and any output typed `cover_up`/`cover_down`, is represented only by the cover. PWM outputs are never cover endpoints.

Read-only entities carry no `command_topic`; a command that still arrives on the `/set` topic is dropped with a warning. `binary_sensor` entities read the switch state topic; `sensor` (%) entities read the number state topic, or `light/{id}/percent` for a former light. Changing `type` or `writable` clears the stale discovery topic of the previous component.

### Switch

A simple on/off relay or PCA output. Appears as a toggle switch in Home Assistant.

```json
{ "id": 2001, "name": "Garden pump", "type": "switch", "enabled": true }
```

### Dimmer (light)

A PWM-capable output exposed as a dimmable light in Home Assistant. Brightness commands are 0–255 (raw myIO value, sent as-is).

```json
{ "id": 2002, "name": "Living room dimmer", "type": "light", "enabled": true }
```

### Number

A PCA or PWM output exposed as a generic number slider (0–100%) in Home Assistant; the bridge scales it to the device's raw 0–255 (`raw = round(pct × 255 / 100)`) and back. Use this instead of `"light"` when the output controls something that is not a lamp — for example:

- Mixing valves (floor heating, solar collector)
- Circulation or irrigation pumps with variable speed
- Fans or ventilation dampers
- Any actuator where a percentage is more meaningful than a brightness level

```json
{ "id": 102, "name": "Floor heating mixing valve", "type": "number", "enabled": true }
```

### Cover (shutter / blind)

A cover is defined in the `"covers"` section and references two outputs — one for the UP direction and one for DOWN. The myIO server's built-in motor protection (preventing simultaneous activation) is respected.

```json
{
  "id": "bedroom_blind",
  "name": "Bedroom blind",
  "enabled": true,
  "up":   { "type": "pca", "id": 2003 },
  "down": { "type": "pca", "id": 2004 }
}
```

The `"type"` field inside `"up"` and `"down"` can be `"pca"` or `"relay"`. Both `up` and `down` are required. Outputs referenced by an enabled cover that also appear in `"pca"` or `"relays"` get no standalone entity — the bridge excludes them automatically. A cover cannot be `"writable": false`.

### Sensor

Sensors are listed in the `"sensors"` section. The bridge reads their values from the myIO server and publishes them as read-only HA sensor entities.

```json
{ "id": 1, "name": "Outdoor temperature", "enabled": true }
```

#### Logging thresholds

Three server-level fields control log verbosity (all generated by discovery with their defaults):

| Field | Type | Default | Description |
|---|---|---|---|
| `sensor_log_threshold` | number | `0.1` | Min. change (°C / unit) required to write a sensor log line; `0` = log every MQTT publish |
| `log_startup_sync` | bool | `false` | Log all entity states during startup and broker-reconnect resync |
| `log_debug` | bool | `false` | Log the per-command `[coalesce]` and `[latency]` measurement lines |

MQTT publishes always happen regardless of these settings — they only suppress log output.

Example — log only changes ≥ 0.5°C and keep startup quiet (default):

```json
"sensor_log_threshold": 0.5,
"log_startup_sync": false
```

Individual sensors can override the server threshold with a per-sensor `log_threshold` field. Set it to `0` to log every publish for that sensor, or to a higher value to reduce noise from a noisy sensor. Omit the field (or set it to `-1`) to use the server-level default.

```json
"sensors": [
  { "id": 1, "name": "Outdoor temperature", "enabled": true },
  { "id": 2, "name": "Floor temperature",   "enabled": true, "log_threshold": 0.5 },
  { "id": 3, "name": "Power meter",         "enabled": true, "log_threshold": 10.0 }
]
```

The Visual editor exposes the per-sensor threshold as a small **Δ** field in each sensor row (`-1` = server default).

## MQTT topics

All topics are prefixed with `topic_prefix` (default: `myio`).

| Entity | State topic | Command topic |
|---|---|---|
| Switch | `myio/{server}/switch/{id}/state` | `myio/{server}/switch/{id}/set` |
| Light | `myio/{server}/light/{id}/state` | `myio/{server}/light/{id}/set` |
| Light brightness | `myio/{server}/light/{id}/brightness` | `myio/{server}/light/{id}/brightness/set` |
| Number | `myio/{server}/number/{id}/state` | `myio/{server}/number/{id}/set` |
| Cover | `myio/{server}/cover/{cover_id}/state` | `myio/{server}/cover/{cover_id}/set` |
| Read-only light/number (`sensor` %) | `myio/{server}/light/{id}/percent` (former light) or `myio/{server}/number/{id}/state` | — |
| Sensor | `myio/{server}/sensor/{id}/state` | — |
| Bridge availability | `myio/bridge/availability` | — |
| Server availability | `myio/{server}/availability` | — |

All state and availability topics are published with `retain = true`. Discovery messages are retained too; the discovery configs never set `retain`, so HA's `/set` commands are not retained.

Home Assistant auto-discovery messages are published to the standard `homeassistant/` prefix. Each entity carries a device block (one device per myIO server, `via_device` the bridge device), an `origin`, and `default_entity_id`.

### Availability

- `<prefix>/bridge/availability` is the bridge's MQTT Last Will. Payloads are `online` / `offline`. `online` is published after connecting (overriding a retained `offline` of a crash); `offline` on clean shutdown or by the broker via the Will.
- `<prefix>/<server_id>/availability`: `online` after the first successful poll (and again on recovery); `offline` only after **3 consecutive failed polls**, so a short W5100 hiccup does not flap the entities.
- Every entity lists both topics with `availability_mode: all` — it is available only while the bridge and its server are both online.
- A diagnostic `binary_sensor` (`myIO bridge` device, device class `connectivity`) shows the bridge's state from the bridge availability topic; it has no availability of its own.

### Diagnostic entities

Zero extra requests reach the myIO devices: everything comes from the already running poll.

- **Per server** (`myIO <server>` device, `entity_category: diagnostic`): the retained JSON topic `<prefix>/<server_id>/diag` (`last_poll_ok`, `poll_latency_ms`, `consecutive_errors`, `total_errors`, `last_error`, `firmware`, `info_error`) feeds seven sensors: **Utolsó sikeres poll** (`timestamp`), **Poll-késleltetés** (`duration`, ms — the time of the last successful `async_poll()`), **Egymást követő poll-hibák**, **Poll-hibák (indulás óta)** (`total_increasing`, resets at bridge start), **Utolsó poll-hiba** (kept after recovery, `nincs` if none), **Firmware-verzió** and **Utolsó info-hiba**. Unique ids: `myio_<server>_diag_<last_poll|poll_latency|consecutive_errors|total_errors|last_error|firmware|info_error>`.
- The diag JSON is published after a poll when it is the first one, after a resync or a firmware change, when the error state changed (first failure, recovery, new error message), and otherwise at most every 60 s. A failed publish is retried after the next poll.
- These sensors use **only the bridge availability topic**, not the server's, so they stay visible (and show the error) while the server is offline.
- **Bridge** (`myIO bridge` device): the **Indulás** sensor (`timestamp`, `entity_category: diagnostic`, unique id `myio_bridge_started`) shows the bridge process start time from the retained `<prefix>/bridge/started` topic, republished with every `online` (startup and reconnect).

## Command latency & TCP delayed-ACK

### The coalesce window

When Home Assistant fires an action that touches several outputs at once (a scene, or an
automation that turns on two lamps), it publishes several MQTT commands back-to-back. The bridge
waits `coalesce_window_ms` after the first command so these siblings arrive and go out to the myIO
device as **one** HTTP POST instead of several. This matters because the myIO Ethernet module
(W5100) has only 4 TCP sockets — bursts of rapid POSTs can exhaust them and make the web server
unreachable for ~1 minute.

The window is a trade-off:

- **Every** command waits `coalesce_window_ms` before being sent, so the value is pure latency for
  the common case of a *single* command (e.g. tilting one blind).
- If the window is shorter than the spread between sibling commands, a sibling misses the batch and
  becomes a second POST — not dangerous (two sequential POSTs, not a burst), but that command lands
  one HTTP round-trip (~0.6–1.5 s) later.

The default is **5 ms**: comfortably above the typical ~1 ms sibling spread on a healthy network,
while keeping single-command latency negligible. With `"log_debug": true` on the server the bridge
logs let you size it for your own traffic — `[coalesce] sibling +Nms after batch start` shows how far each sibling landed from the
batch start, and `[coalesce] batch closed: N commands within Wms window` summarises each batch. If
you see siblings regularly arriving at, say, 8 ms, raise the window for that server; if you never
batch anything, you can lower it toward `0`.

### Diagnosing a stable ~40 ms sibling gap (TCP delayed-ACK)

If the `[coalesce] sibling +Nms` log shows a **stable ~40 ms** gap (not a jittery few ms), the delay
is almost certainly **not** in the bridge — it is a classic TCP **Nagle × delayed-ACK** stall on the
**Home Assistant → MQTT broker** connection, and it will silently force you to keep the coalesce
window at ≥ 40 ms.

**What happens:** HA's MQTT client (paho) sends the command burst with Nagle's algorithm enabled, so
it won't put the 2nd/3rd small packet on the wire until the 1st is acknowledged. The broker, as the
*receiver*, delays that ACK by up to ~40 ms (Linux `TCP_DELACK_MIN`, visible as `ato:40` in
`ss -ti`). So HA stalls ~40 ms between packets. The effect only appears on an **idle / cold**
connection — a warm connection (recent traffic) is already in quickack mode and shows a few ms. That
is why the symptom is most visible at night or after a quiet period. It is *not* the bridge: a
loopback publish straight into the broker is delivered to the bridge in 0 ms.

**The fix — receiver-side `TCP_QUICKACK`, applied as a route "trick" on the broker host.** Disabling
Nagle on the sender (HA) or setting `set_tcp_nodelay` on the broker does **not** help — those are the
wrong (sender-side) knob. The reliable fix is to make the **broker** ACK immediately, by setting
`quickack 1` on the route the broker uses to reach HA:

```bash
# On the broker host, for the subnet that contains Home Assistant.
# Adjust the network / dev / src to match `ip route`.
ip route change 10.0.0.0/16 dev eth0 proto kernel scope link src <broker-ip> quickack 1
```

Verify with the bridge log: the next idle-connection multi-command action should show
`[coalesce] sibling +1ms` instead of `+40ms`. (Note: `ss` still reports `ato:40` — that field is the
delayed-ACK *constant*, not proof that quickack is off; the real proof is the measured sibling gap.)

Make it persistent (survives reboot) by adding a `post-up` hook to the broker's interface, e.g. in
`/etc/network/interfaces` (ifupdown):

```
iface eth0 inet static
	address <broker-ip>/16
	gateway <gw>
	post-up ip route replace 10.0.0.0/16 dev eth0 proto kernel scope link src <broker-ip> quickack 1
```

**Caveat — you need `NET_ADMIN`.** The route trick requires the `CAP_NET_ADMIN` capability. It works
on a normal host, a VM, or a container that has the full capability set. On a **locked-down or
capability-restricted container** the `ip route change` may appear to succeed but not take effect
(the sibling gap stays ~40 ms). This is the main reason to run the broker somewhere you control the
network stack — a dedicated LXC/VM rather than an appliance that hides it (e.g. a closed
Home-Assistant-OS add-on). Once the stall is gone, you can safely lower `coalesce_window_ms`.

## Deploying to Linux (LXC / VM)

Pre-built static binaries are available on the [Releases](../../releases) page. The `install.sh` script automates the full first-time setup on a Debian/Ubuntu host.

### Requirements

- Debian Trixie or Ubuntu 24.04+
- `git` (installed by `install.sh` if missing)
- A GitHub PAT (classic) with `repo` scope — needed to download release assets from a private repository

### First-time install

```bash
# Set the token
export GITHUB_TOKEN=ghp_...

# Clone the repo (do NOT embed the token in the URL — it would persist in .git/config)
git -c http.extraheader="Authorization: basic $(printf 'x-access-token:%s' "$GITHUB_TOKEN" | base64 -w0)" \
    clone https://github.com/pvaczi/myio_bridge /opt/myio-src

# Run the installer as root
bash /opt/myio-src/install.sh
```

`install.sh` does the following:

- Installs `curl`, `git` and `python3-venv`
- Creates a `myio` system user
- Creates `/opt/myio-bridge/{bin,data}`
- Writes the token to `/etc/myio-bridge.env` (mode 600)
- Copies the Web UI and sets up a Python venv (pinned deps from `web/requirements.txt`)
- Generates a Web UI password into `/opt/myio-bridge/data/webui_password` (login: `admin`)
- Copies `bridge.json` and `discovery_input.json` (only if not already present — existing configs are preserved) and restricts them to mode 600 (they contain the myIO passwords in plain text)
- Installs `myio-bridge.service` (with systemd sandboxing) and `myio-web.service`
- Configures sudoers (validated with `visudo -cf`) so the Web UI can start/stop the bridge
- Downloads the latest binary via `update.sh` and starts both services

The script is idempotent — re-running it is safe and will not overwrite existing config files.

### Updating

```bash
sudo bash /opt/myio-src/update.sh
```

This does everything in one step, with several safety nets added after a disk-full
incident produced a truncated binary in production:

1. **Preflight**: checks free space on both the install dir and the temp dir before touching anything
2. `git pull` on `/opt/myio-src` (or clones it if missing) — the token is passed as an ephemeral `http.extraheader`, never stored in `.git/config`
3. Copies the updated Web UI files to `/opt/myio-bridge/web/` and restarts `myio-web`
4. Downloads the latest release archive **to a temp dir**, then verifies it before the swap: sha256 digest against the GitHub API (when available), `tar -tzf` archive integrity, and a `--version` run of the extracted binary
5. Atomically swaps the binaries with `.bak` backups; on any install or startup failure it rolls back to the backups and restarts the old version
6. Restarts `myio-bridge` (only if it was running before) with a two-stage health check; the `.bak` files are kept as last-known-good

`update.sh` also syncs the unit files (`myio-bridge.service`, `myio-web.service`) from the repo to `/etc/systemd/system/` before the restart (`cmp` + copy + one `daemon-reload` if anything changed).

### systemd integration

`myio-bridge.service` is `Type=notify` with `WatchdogSec=60`, no libsystemd needed (the bridge writes to `$NOTIFY_SOCKET` itself):

- `READY=1` is sent as soon as the event loop runs — not tied to the MQTT connection, so a broker that is down at boot does not fail the unit start
- `STATUS=` shows the MQTT state in `systemctl status` (`MQTT connected` / `MQTT disconnected, reconnecting`); `STOPPING=1` on SIGTERM/SIGINT
- `WATCHDOG=1` is pinged every 30 s from the event loop. It proves only that the loop is alive (independent of myIO polling and MQTT); if it stops, systemd kills the process and `Restart=on-failure` restarts it

### Logs

```bash
journalctl -u myio-bridge -f
journalctl -u myio-web -f
```

## Web UI

The bridge ships a lightweight web interface (`myio-web.service`, port 8080) for monitoring and control without a terminal.

Access is protected by HTTP Basic auth. Credentials live in `/opt/myio-bridge/data/webui_password` in `username:password` format (single line; `install.sh` generates a random user like `myio-x7k2ab` and a random password, and prints both at the end of the install). To change them, edit the file and restart `myio-web`. A line containing only a password (no colon) falls back to the legacy username `admin`. If the file is missing, the UI runs unauthenticated — delete it only on a fully trusted network.

Features:
- **Bridge mode** (default): start/stop the bridge, edit `bridge.json`, view the live log
- **Discovery mode**: run discovery (with confirmation — merges into `bridge.json`, see the discovery re-run rules), edit `discovery_input.json`; only available when the bridge is stopped
- **Szerverek kártya**: szerverenként élő állapot (online/offline, utolsó poll, késleltetés, hibaszámok, firmware), 10 másodpercenként frissül, amíg az oldal látható. A bridge a `data/status/<server_id>.json` fájlokba írja (a `bridge.json` mappájába, atomikusan, MQTT-től függetlenül); az `elavult` jelző azt jelzi, hogy a fájl 180 s-nál régebbi (a bridge valószínűleg áll).
- **Live log**: last 200 lines of the bridge's systemd journal, with manual refresh or auto-refresh every 3 seconds
- **`bridge.json` editor**: opens in a resizable, draggable floating popup (760×560 px). Toggle between **Raw** (plain textarea) and **Visual** modes via the button in the popup header.
  - **Save** validates with `bridge --check-config` and refuses an invalid file; **Mentés és újraindítás** also restarts the bridge (at most once per 10 s — every restart re-polls each myIO server).
  - Every save that changes the file first copies the previous version to `data/bridge.json.bak.<YYYYMMDD-HHMMSS>` (newest 5 kept); the footer drop-down + **Visszaállítás** restores one (the current file is backed up first, the bridge picks it up on its next restart).
  - **Visual mode** — a custom form editor built on Bootstrap; no external library required:
    - Collapsible sections for MQTT, each server, and per-server device groups (PCA, Relays, PWM, Sensors, Covers)
    - Each device fits on a single line: `id · name · type · sensor-id (S:) · enabled · delete`
    - Cover entries show both endpoints inline: `↑ type/id · ↓ type/id · timeout`
    - Live filter by device name or ID; add/delete servers and individual devices
    - Server header (id + host) updates in real time as you type
    - Diagnostic fields generated by discovery (`_sensor_id`, `_pwm`, `_protection_index`, `_name`) are preserved on save
  - **Raw mode** — plain textarea for direct JSON editing; switching back from Visual syncs all changes

Access it at `http://<host-ip>:8080` after installation.

## myIO HTTP API

The bridge communicates with myIO servers using their built-in HTTP API:

| Endpoint | Method | Description |
|---|---|---|
| `/d_sens_out.json` | GET | Full device state (used by discovery) |
| `/sens_out.json` | GET | Current state (used by bridge polling) |
| `/info.json` | GET | Server name and firmware version (fetched at startup) |
| `/` | POST | Send commands (see table below) |

Authentication uses HTTP Basic Auth.

### Command handling

Payloads are validated strictly (case-insensitive, whitespace trimmed); anything else — including an empty payload such as a retained-clear — is dropped with a warning: no POST, no state publish.

| Entity | Accepted payload |
|---|---|
| switch, light on/off | `ON` / `OFF` |
| light brightness | integer 0–255 |
| number | integer 0–100 (%), sent as raw 0–255 |
| cover | `OPEN` / `CLOSE` / `STOP` |

Also dropped: commands whose topic component does not match the output's configured type, read-only outputs, and cover endpoints. A POST answered with HTTP 401, 4xx or 5xx is an error (3xx is accepted); the optimistic state is then **not** published. An empty response or one without a status line is a failed exchange and is retried like a connection error.

### POST commands

| Command | Example | Description |
|---|---|---|
| `PCA_ON={id}` | `PCA_ON=2005` | Turn PCA output on |
| `PCA_OFF={id}` | `PCA_OFF=2005` | Turn PCA output off |
| `PCA*{id}={raw}` | `PCA*2005=191` | Set PCA PWM output to raw 0–255 (number: 75 % → 191) |
| `r_ON={id}` | `r_ON=3` | Turn relay on |
| `r_OFF={id}` | `r_OFF=3` | Turn relay off |
| `f_ON={id-100}` | `f_ON=1` | Turn PWM output on (id 101 → use 1) |
| `f_OFF={id-100}` | `f_OFF=1` | Turn PWM output off |
| `fet*{id-100}={raw}` | `fet*1=191` | Set PWM output to raw 0–255 |
